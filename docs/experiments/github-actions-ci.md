# GitHub Actions findings for LoginGuard

Research checked on 27 November 2026. The foundation milestone needs a clean checkout that runs Maven verification against fresh PostgreSQL and runs frontend lint and a TypeScript-checked production build. The checkout already contains the toolchain lockfile, dependency lockfile, Maven Wrapper and database tests needed for those checks. [Current handoff](../ROADMAP.md#current-handoff) · [Local development checks](../../README.md#development)

## What the sources establish

**A pull request run can verify the proposed merge.** For an open pull request, GitHub's default checkout uses the test merge commit, while a push run checks the pushed commit. Filtering a required workflow by path can leave its check pending. For LoginGuard, running backend and frontend checks on every PR to `main` and on pushes to `main` would also cover changes to shared files such as `mise.lock`. GitHub recommends unique job names across workflows when those names are used as required checks. [GitHub workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) · [Checkout](https://github.com/actions/checkout) · [Skipped checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#handling-skipped-but-required-checks) · [Branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#about-branch-protection-rules)

**The committed lockfiles already cover a hosted Linux runner.** GitHub offers fresh Ubuntu x64 VMs, including the explicit `ubuntu-24.04` label. LoginGuard's mise lock records Linux x64 download URLs and checksums for Temurin 25.0.5.1+2 and Node 26.13.1. The mise action can install from that lock automatically, and its own mise binary version is a separate input. The Maven Wrapper selects Maven 3.10.1, and `verify` includes the test phase. `npm ci` fails if the package manifest and lockfile disagree, and the frontend build runs TypeScript checking before Vite. [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#standard-github-hosted-runners-for-public-repositories) · [mise lockfile](../../mise.lock) · [mise CI guidance](https://mise.jdx.dev/continuous-integration.html) · [Released action inputs](https://raw.githubusercontent.com/jdx/mise-action/924e7c586e33d7d4bae9c14e26c5d22e2beb6e78/action.yml) · [Wrapper configuration](../../backend/.mvn/wrapper/maven-wrapper.properties) · [Maven lifecycle](https://maven.apache.org/guides/introduction/introduction-to-the-lifecycle.html) · [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/) · [Frontend scripts](../../frontend/package.json)

**A job-scoped PostgreSQL service fits the existing migration check.** GitHub creates a fresh service container for each job and can assign its published port dynamically. Spring already reads `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER` and `POSTGRES_PASSWORD`, so the service can use disposable credentials and supply its mapped port to Maven. A Docker health check using `pg_isready -h 127.0.0.1` checks TCP readiness. The official image starts a temporary socket-only server during initialization, which can respond to a socket probe before the TCP server is available. LoginGuard's migration test checks the successful Flyway V1 history entry and the four columns of `public.users`. That test provides evidence for initialization on a fresh database. [GitHub PostgreSQL example](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers) · [Service port mapping](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idservices) · [Spring configuration](../../backend/src/main/resources/application.yaml) · [PostgreSQL image entrypoint](https://github.com/docker-library/postgres/blob/master/docker-entrypoint.sh) · [pg_isready](https://www.postgresql.org/docs/17/app-pg-isready.html) · [Migration test](../../backend/src/test/java/com/loginguard/loginguard/DatabaseMigrationTests.java)

**The build can run with read-only repository access.** GitHub recommends minimum token permissions and full commit SHAs for action pins. Ordinary fork PRs normally receive a read-only token, and repository settings determine whether a maintainer must approve the run. Checkout supports disabling credential persistence. The mise action also keeps its token within the setup step by default as of v5.1.1. These controls fit a build whose inputs are public dependencies and a disposable database. [GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use) · [Fork PR behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) · [Checkout inputs](https://github.com/actions/checkout#usage) · [mise token change](https://github.com/jdx/mise-action/releases/tag/v5.1.1)

**Cache contents and image tags affect what a clean run can reproduce.** The mise action's default cache restores installed tools directly, while mise checks cached downloads against lockfile hashes before using them. An uncached first run would establish how long the clean path takes and give LoginGuard a baseline for deciding whether package download caches are worthwhile. The `postgres:17` tag matches local Compose and lets CI pick up patch releases. A digest would identify the exact image if a later release needs to reproduce a run. ## Recommendation for the foundation milestone

One CI workflow with independent backend and frontend jobs fits the current repo. The backend job would use a fresh PostgreSQL 17 service and Maven Wrapper verification. The frontend job would install from the npm lockfile and run the existing lint and build scripts. The first hosted run would provide the tested commit, effective tool versions, the context and migration test results, and the frontend results. The run URL is the evidence the handoff calls for.
